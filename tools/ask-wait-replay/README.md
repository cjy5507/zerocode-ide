# ask-wait-replay — 질문자가 받는 쪽에 대해 알 수 있던 것을 원장으로 재는 하네스 (t-6740)

두 조각이다. `seed.py` 는 **모으기만** 하고, 규칙은 하나도 갖지 않는다 — 무엇이 알림이 되는지는
`crates/zerocode-core/src/orchestration.rs` 의 `ReceiverNews` 표 한 곳, 「답」의 정의는
`Message::answers` 한 곳이다. 파이썬에 규칙 사본이 생기면 재는 규칙과 나가는 규칙이 갈라진다.

| 조각 | 무엇 |
| --- | --- |
| `tools/ask-wait-replay/seed.py` | 창의 권한 저장소(`~/Library/Application Support/dev.zerocode.app/authority/authority.sqlite`, **읽기 전용 `mode=ro`**)에서 원장 **하나**의 뿌리 질문마다 — 누가 누구에게(주소 머리만), 기다림이 어떻게 끝났는지(`answered`·`closed`·`censored`), **기준선**(받는 쪽이 워커면 그동안 원장이 그 워커에 대해 적은 사실: 턴 끝·멈춤·판정 사유·쿼터 벽·시도 끝남과 그 기록), **알림**(규칙이 질문 스레드에 적은 `ledger` 의 `status` 줄: 사유 낱말·최종 여부·사실 시각·적힌 시각) — 을 씨앗 한 행으로 |
| `tools/tests/test_ask_wait_replay_seed.py` | 씨앗이 질문 뒤에 적힌 사실만 싣는지, 원장 자신의 줄을 답으로 읽지 않는지, 원장 하나만 읽는지, 결말을 원장의 기록으로만 부르는지, 알림 줄을 읽되 조언 문장은 안 옮기는지, 원장을 한 바이트도 안 움직이는지, 본문이 새지 않는지, 상수가 Rust 원본과 같은지 (`just tools-test`) |

## 돌리기

```sh
python3 tools/ask-wait-replay/seed.py --out /tmp/ask-wait/seed.json      # 요약 표를 찍고 씨앗을 남긴다
python3 tools/ask-wait-replay/seed.py --db <복사본.sqlite> --out …          # 다른 저장소
python3 tools/ask-wait-replay/seed.py --db … --ledger-id <id> --out …      # 원장이 여럿인 저장소
```

## 이 하네스가 지키는 것

1. **질문 당시 알 수 있던 것만.** 받는 쪽의 사실과 알림은 원장이 그것을 **적은 시각**(`learned_ms`)이 질문 뒤·기다림 끝 전일 때만 싣고, 사실의 제 시각(`fact_ms`)을 따로 둔다. 기다림의 끝은 답이 온 시각, 질문자의 dispatch 가 끝난 시각, 아니면 원장의 마지막 쓰기(오른쪽 censoring — 따로 센다).
2. **답은 원장의 정의로.** 스레드에서 물은 자리의 줄이되 원장 자신의 목소리·원장만 쓰는 종류는 답이 아니다. 예전의 느슨한 읽기가 답으로 삼았을 줄이 다르면 `misread_answer` 로 센다.
3. **원장 하나.** 저장소의 모든 행은 `ledger_id` 로 갈리고 id 는 원장마다 새로 발급되므로, 두 원장이 같은 `m-1` 을 가질 수 있다. 모든 읽기를 한 `ledger_id` 로 좁힌다 — 저장소에 원장이 하나면 그것, 여럿이면 `--ledger-id` 없이는 거절(종료 코드 2).
4. **결말은 그 시도의 기록으로만.** 받는 쪽 시도가 기다림보다 먼저 끝났을 때 `died`(`worker_died` 행)·`done`(`worker_done` 행) — 둘 다 **그 시도의 dispatch 키**로 적히고 그 시도가 끝난 시각까지 적힌 행만 — ·`stopped`/`abandoned`(원장이 **그 시도의** 과업 결과에 적은 `outcome` — 과업 결과는 다음 시도가 덮어쓰므로 그 시도가 과업의 마지막 시도일 때만 읽는다)로 부르고, 원장이 읽을 수 있는 까닭을 남기지 않았으면 `unexplained` 다. 까닭 없는 끝을 정지로 추정하지 않고, 같은 워커의 **다음 시도**의 사망·보고나 시도 키가 없는 행을 워커 id와 대기 구간만으로 이 시도의 결말로 붙이지 않는다(t-6740 r3).
5. **원장은 아무 데도 안 움직인다.** `mode=ro` 로 열고, 씨앗에는 해시 id·주소 머리·낱말·수치만 남는다. 본문·조언 문장·정지 사유 산문은 한 글자도 나가지 않는다.
6. **분모를 나눠 적는다.** 받는 쪽이 워커인 질문 중 「열린 시도가 없던 워커」·「사실이 하나도 안 적힌 워커」·「시도가 먼저 끝난 워커」를 따로 세고, 기준선에서 코디네이터·판 수신자는 `unobservable` 로 둔다 — 규칙 전의 원장은 코디네이터 판의 턴을 적지 않았다는 사실을 수치로 꾸미지 않는다.

## 무엇을 재고 무엇을 못 재나

- **기준선**(`receiver_facts`·`turn_ends`·`stalls`·`judged`·`quota_walls`·`receiver_ended`)은 규칙 **전**에 원장이 이미 적던 관측(`went_quiet`·`quota_walled`, 결말은 시도 키로 적힌 `worker_died`·`worker_done`)만 읽는다. 규칙 전의 원장에서 코디네이터·판 수신자는 늘 `unobservable` 이다.
- **알림**(`notices`)은 규칙이 적은 줄을 읽는다. 규칙 전의 원장에는 한 줄도 없고, 규칙 뒤의 원장에서는 코디네이터·판 수신자에게도 생긴다 — 그 원장을 다시 돌리면 코디네이터 수신자의 첫 숫자(사유별 사실→행 지연 p50/p95, 최종 낱말 수)가 여기서 나온다.
- 「규칙 뒤 답 없는 대기가 얼마나 줄었나」를 같은 역사 위에서 계산한 값은 **정책 재생 추정**이다 — 배포 뒤 사용자가 실제로 덜 기다린 실측이 아니다. 실측은 규칙 뒤 원장의 `notices` 와 대기 끝을 이 도구로 다시 읽어야 나온다.
